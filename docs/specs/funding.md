# 포인트 펀딩 엔진 스펙

돈 대신 포인트로 동작하는 크라우드펀딩. 창작자가 목표 T·보상풀 R·마감 D로 펀딩을
개설하고, 후원자가 포인트로 참여해 지분을 얻는다. 100% 달성 시 성공 정산, 마감까지
미달성이면 실패로 종료된다.

용어: T=목표 포인트, R=보상풀(창작자 예치), D=마감시각, raised=현재 모인 합,
c_i=후원자 i의 기여금, 지분_i = c_i / T (성공 시 확정), CAP=1회 참여 상한.

## 불변식 — 각각 참/거짓 판정 가능. 위반 시 동작·강제 위치 명시

### 잔액·참여
- INV-BAL-1: 모든 사용자 잔액은 정수이며 항상 ≥ 0. 어떤 연산도 잔액을 음수로 만들 수
  없다. 위반이 될 연산은 거절되고 상태는 불변. (강제: 서버)
- INV-BAL-2: 참여 금액 c는 정수이며 `1 ≤ c ≤ min(CAP, 후원자잔액, T−raised)`.
  하나라도 위반이면 참여 거절 — 잔액·raised 불변. (강제: 서버)
  - `T−raised` 상한 때문에 raised는 T를 초과할 수 없다(=목표 초과 참여 거절, "정확히 100%까지").

### 펀딩 수명주기
- INV-FUND-1: 개설 시 `T>0`, `D`는 미래, `R≥0`, `창작자잔액 ≥ R`. 하나라도 위반이면
  개설 거절. 개설 성공 시 창작자 잔액 `−= R` (보상풀 잠금). (강제: 서버)
- INV-FUND-2: 상태는 `OPEN → (SUCCESS | FAILED)` 단방향. 종료 후 상태 전이·참여·정산
  재실행 불가(멱등 — 재호출해도 추가 효과 없음). (강제: 서버)
- INV-FUND-3: `raised == T`가 되는 그 참여 트랜잭션에서 즉시 `SUCCESS`로 전이하고 성공
  정산(INV-SET-1)이 정확히 1회 실행된다. (강제: 서버)
- INV-FUND-4: `현재시각 ≥ D` 이고 `raised < T`이면 `FAILED`로 전이. `현재시각 ≥ D`
  이후 어떤 신규 참여도 수용되지 않는다. (강제: 서버, 마감 판정은 서버 시계)

### 정산 — 성공
- INV-SET-1: `SUCCESS` 시 창작자 잔액 `+= T`(달성금). 보상풀 R을 후원자에게 지분비율로
  분배: `reward_i = floor(R × c_i / T)`. 후원자 기여금 c_i는 **반환하지 않는다**. (강제: 서버)
- INV-SET-2 (총량 보존): 성공 정산 전후 시스템 총 포인트 합은 **불변**. 반올림 잔여
  `rem = R − Σ floor(R×c_i/T)`는 소수부 `frac(R×c_i/T)`가 큰 후원자부터 1P씩 배분(동률은
  먼저 참여한 순). 결과 `Σ reward_i == R` — 반올림으로 포인트가 생기거나 사라지지 않는다. (강제: 서버)

### 정산 — 실패
- INV-SET-3: `FAILED` 시 모인 기여금 `Σ c_i`는 **소각**(어떤 계정에도 귀속 안 됨).
  보상풀 R은 창작자에게 **반환**(창작자 잔액 `+= R`). 실패로 인한 시스템 총량 감소분은
  정확히 `Σ c_i`. (강제: 서버)

### 동시성·접근
- INV-CONC-1 (원자성): 참여 = [잔액검사·차감 + raised 증가 + `T−raised` 검사 + 성공전이]가
  **단일 트랜잭션**. 동시 참여가 `raised > T`, 잔액 음수, 또는 이중 성공전이를 만들 수 없다.
  (강제: 서버 Postgres 트랜잭션/RPC)
- INV-ACC-1: 클라이언트는 잔액·raised·상태·정산을 **직접 쓸 수 없다**. 모든 변경은 서버
  RPC 경유. 클라가 보낸 금액·펀딩id·**현재상태**는 신뢰하지 않고 서버에서 재검증.
  (강제: 서버 · .claude/rules/supabase.md)
  - ⚠️ 데모 한정 예외: **행위자 신원(사용자id)은 서버가 검증하지 않는다.** 실제 로그인이
    없어 currentUser 닉네임을 클라가 정해 RPC에 넘기고, 서버는 그 닉네임을 신뢰한다.
    금액·잔액·상한·상태·자기펀딩·마감·동시성은 전부 서버가 강제하므로 포인트를 무에서
    창조하진 못하지만, 데모 계정 간 **사칭·공유상태 훼손**은 가능하다. 공개 배포 시
    반드시 Supabase Auth + `auth.uid()` 바인딩으로 행위자를 세션에서 취득해야 한다.
- INV-SELF-1: 창작자는 자신이 개설한 펀딩에 참여할 수 없다. 위반 시 거절. (강제: 서버)

## 시나리오 — 각각 검증 불변식 ID 참조 (불변식마다 실패 경로 1개 이상)
- S1 (INV-BAL-1, INV-BAL-2): 잔액 500 사용자가 600 참여 시도 → **거절**, 잔액·raised 불변.
- S2 (INV-BAL-2, INV-FUND-3): raised=900, T=1000에서 200 참여 시도 → 남은 100 초과라 **거절**.
  이어 100 참여 → raised=1000 → `SUCCESS` 전이.
- S3 (INV-FUND-3, INV-SET-1, INV-SET-2): T=1000, R=300. A가 600, B가 400 참여로 달성 →
  창작자 `+1000`, A `+= floor(300×600/1000)=180`, B `+=120`. `Σreward=300=R`, 총량 보존.
- S4 (INV-SET-2 반올림): T=1000, R=100. 세 후원자 333/333/334 → floor 33/33/33(합 99),
  잔여 1P는 소수부 최대(334) 후원자에게 → 33/33/34, `Σ=100`.
- S5 (INV-FUND-4, INV-SET-3): T=1000, raised=700, `현재시각≥D` → `FAILED`. 후원자 700
  **소각**(환불 없음), 창작자 보상풀 R **반환**. 시스템 총량 `−700`.
- S6 (INV-FUND-2): `SUCCESS`된 펀딩에 추가 참여/재정산 호출 → **무효**(멱등), 상태·잔액 불변.
- S7 (INV-CONC-1, INV-FUND-3): raised=990, T=1000에서 두 사용자가 동시에 각 10 참여 →
  **하나만** 성공전이(raised=1000), 다른 하나는 남은 0으로 **거절**. raised는 1000 초과 안 함.
- S8 (INV-SELF-1): 창작자가 자기 펀딩에 참여 시도 → **거절**.
- S9 (INV-FUND-1): 창작자 잔액 200인데 R=300으로 개설 시도 → **거절**.
- S10 (INV-FUND-4): `현재시각≥D` 이후 도착한 참여 → **거절**(마감 후 참여 불가).

## 신뢰 경계
- **믿는 값**: 서버 DB의 잔액·raised·status·contributions·마감시각(D)·서버 시계.
- **믿지 않는 값**: 클라이언트가 보낸 금액 c·펀딩id·클라이언트 시계·클라가 표시한
  현재 상태. 전부 서버에서 재검증.
  (예외: 사용자id/행위자 신원 — 데모라 서버가 검증하지 않음. INV-ACC-1의 ⚠️ 참조)
- **강제 위치**: 모든 금융 연산(차감·정산·소각·상태전이)은 Postgres RPC/트랜잭션. 클라이언트는
  호출·표시만 한다.

## 확정 파라미터 (2026-07-07 승인)
- CAP(1회 참여 상한) = **5,000 P** (상수)
- 데모 계정 초기 지급 = **10,000 P**
- INV-SELF-1(자기 펀딩 금지) **채택**
- 마감 판정: 별도 크론 없이 **접근 시 지연 평가(lazy)** — 펀딩 조회/참여 시 `현재시각≥D`면
  그 자리에서 FAILED 정산 (데모 범위)
- 금액 단위는 정수 포인트(소수 없음)
